### Mindcraft を土台にしなかった理由

- Mindcraft の記憶は「会話の要約」を中心とした仕組みで、今回の中心である **SQLite の個人記憶・共有の歴史・日記・関係の変化・死亡と墓・LLMの優先度キュー** を入れるには、エージェントの中核 (会話ループ・プロンプト・記憶) をほぼ書き換えることになる
- 本体はクラウドAPI 15種以上の SDK、ブラウザUI、画像描画 (canvas / WebGL) などの依存が多く、`canvas` などのネイティブ依存は Windows で `npm install` が失敗しやすい (Mindcraft 自身も FAQ でトラブル対処を案内している)
- 一方、**Minecraft を操作する部分は Mindcraft と同じライブラリ** (mineflayer + pathfinder + collectblock + pvp) を使っているので、操作の品質は同じ土台に乗っている

今後、建築・クラフトの高度な処理が必要になったら、Mindcraft の `skills.js` (MIT) から必要な関数だけを移植するのが効率的です。

## 2. LLM の使い方: 9人で1つのモデルを共有する

### 9人別々のモデル vs 1つを共有

| 方式 | VRAM | 判定 |
|---|---|---|
| 9人それぞれ別のモデルを常駐 (7B Q4 ≈ 4.7GB × 9) | 約 45GB 以上 | 家庭用GPUでは不可能。電気代もほぼ変わらず無駄 |
| **1つのモデルを共有** (人格・記憶はプロンプトで毎回切り替え) | 7B: 約 5GB / 14B: 約 9〜11GB | **採用** |

人格・記憶・会話履歴は SQLite に人ごとに分けて保存し、LLMを呼ぶたびに「その人の分だけ」をプロンプトに入れます。
モデルは毎回まっさらな状態で答えるので、1つのモデルを共有しても人格や記憶は混ざりません。

### 順番に処理 vs 同時に処理

| | 順番 (concurrency=1) | 同時 (concurrency=N, OLLAMA_NUM_PARALLEL=N) |
|---|---|---|
| VRAM | モデル + 文脈1人分 | モデル + 文脈 × N人分 (重みは共有、KVキャッシュがN倍) |
| 1回の応答時間 | 最短 | 少し遅くなる |
| 全体の処理量 | 1件ずつ | GPUがまとめて計算するので合計は増える (通常 2〜3倍程度。要実測) |
| 9人の体感 | 9人目は8人分待つ。会話の返事は優先度で割り込む | 待ちが減り、同時に複数人が考えられる |
| 向いている機材 | GTX 1660 SUPER (6GB) | 16〜24GB GPU |

このプロジェクトでは**優先度付きキュー**を入れています: 会話の返事・仲間の死への反応 > 行動の決定 > 日記・記憶整理。
順番処理でも、話しかけられた人がなるべく早く返事できます。

### 応答速度の見積もり (推定・要実測)

1回の判断プロンプトは約3,300文字 (日本語+行動一覧)。Qwen系で 2,000〜3,000 トークン程度と推定。

- GTX 1660 SUPER + 7B Q4: プロンプト読み込み数秒 + 出力 150 トークン (20〜30 token/秒と推定) で **1回 8〜15秒程度**
  - 3人 → 1人あたり 30〜45 秒ごとに次の行動を考える (行動の実行中も他の人の思考が進むので、実際はもう少し短い)
  - 9人 → 1人あたり 1.5〜2分ごと。生活シミュレーションとしては成立するが、会話のテンポは遅い
- 実測は `npm run check` (token/秒) と `npm start -- --minutes 30` 終了時の統計で行う

### モデルの候補

| VRAM | 候補 (Ollama) | メモ |
|---|---|---|
| 6GB (現在) | `qwen2.5:7b-instruct` (Q4_K_M 約4.7GB) | 初期設定。全部GPUに載る |
| 6GB (速さ優先) | `qwen2.5:3b` (約1.9GB) | 速いが判断・日本語の質は下がる |
| 6GB | `qwen3:8b` (約5GB) | 文脈込みで6GBを超え、一部がCPUに回り遅くなる可能性。要実測 |
| 16GB | `qwen3:14b` (約9GB) + 並列 3〜4 | 9人で実用的な速度を狙える |
| 24GB | `qwen3:14b` + 並列 9、または より大きいモデル + 並列少なめ | 質と速度のバランスを実測で決める |

サイズは Ollama 公式ページと第三者のガイドの値 (推定)。新しいモデルは頻繁に出るので、買い替え時に ollama.com/library で再確認します。
Qwen3 は「思考モード」があるため、設定 `think:false` で切っています (切らないと遅くなる)。

## 3. VOICEVOX

- ENGINE を起動すると `http://127.0.0.1:50021` で HTTP API が使える。`/audio_query` で読み方を作り、`speedScale` (速度)・`pitchScale` (高さ)・`intonationScale` (抑揚)・`volumeScale` (音量) を書き換えて `/synthesis` で WAV を得る
- 再生は1本のキューで順番に流し、発言の間に `gap_ms` の間を入れるので会話が重ならない。たまりすぎたら古い発言から捨てる
- 現在は**PCのスピーカーから再生** (Windows は PowerShell の SoundPlayer)。ゲーム内の位置から聞こえる立体音響は、サーバー側のMod/プラグインが必要になるので今後の課題
- 声 (speaker ID) の初期割り当ては下記。**ID は VOICEVOX のバージョンで変わる可能性があるため、`npm run voices` で実際の一覧を確認**してから characters/*.json を直してください

### 利用規約・クレジット (確認できた範囲)

- 音声を使うときはクレジット表記が必要。表記例は「VOICEVOX:ずんだもん」
- **規約はキャラクターごとに別**。東北ずん子プロジェクトのキャラ (ずんだもん・四国めたん・九州そら など) と、それ以外のキャラでは規約が異なる
- 動画では概要欄などにクレジットを書く方法が紹介されているが、これは二次情報。**公式の各キャラクターの規約ページで確認が必要** (今回の調査では公式規約の本文までは取得できなかった)
- いわゆる「ゆっくりボイス」(AquesTalk 系) は用途によってライセンス購入が必要な場合があるため、無料で使うなら VOICEVOX を推奨

## 4. 機材と電気代

### 現在のPC (GTX 1660 SUPER / 6GB)

- 3人の試作は可能 (7B Q4 が丸ごと載る)。9人は「動くが反応が遅い」見込み
- CPU・RAM が未確認。Minecraft サーバー (Java) に 2〜4GB、Node.js (9人分のボット) に 1〜2GB 程度を見込む

### 買い替え候補の考え方 (予算 25〜40万円)

- 最優先は **GPU の VRAM**。16GB あれば 14B モデル + 並列処理で9人が現実的、24GB あれば余裕が出る
- RAM は 32GB で足りる見込み (64GB は大きなモデルを CPU に逃がす場合のみ有効)。9人の試作で実測してから決める
- CPU は Minecraft サーバーのため Ryzen 5〜7 クラスで十分。NVMe SSD は 1TB でも足りるが、ワールドとバックアップを考えると 2TB が安心
- GPU とメモリの価格は変動が大きいため、具体的な型番と価格は**購入直前に再調査**する。3人試作の実測値 (token/秒・VRAM使用量) を基準に「何GBあれば何人が何秒ごとに考えられるか」を計算してから選ぶ

### 24時間稼働の電気代の試算 (推定)

条件: 電気料金 31円/kWh (家電の目安単価)、月30日。LLM はほぼ常に誰かの思考を処理している前提 (9人なら止まらない)。

| 構成 | 平均消費電力 (推定) | 月の電力量 | 月額 |
|---|---|---|---|
| 現在のPC (1660 SUPER, TDP 125W) で3〜9人 | 150〜200W | 108〜144kWh | **約3,300〜4,500円** |
| 16GB GPU (TGP 165〜300W級) で9人 | 200〜320W | 144〜230kWh | **約4,500〜7,100円** |
| 24GB 高性能GPU (TGP 350〜450W級) で9人 | 300〜450W | 216〜324kWh | **約6,700〜10,000円** |
| (参考) 9人別々にLLMを動かす | GPU を9台用意することになり非現実的 | — | — |

- 1つのモデルを共有する限り、**人数を増やしても消費電力はほぼ同じ** (GPU が休む時間が減るだけ)。増えるのは待ち時間
- 節電策: `decide_interval_ms` を長くする、夜間 (人間がいない時間) は人数を減らす、`keep_alive` で使わない時間はモデルを下ろす
- 正確な値はワットチェッカー (1,000〜3,000円程度) で実測するのが確実
